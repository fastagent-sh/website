# FastAgent website

This repository owns the public landing page, rendered documentation, blog, and brand assets for fastagent.sh.

- Framework behavior and onboarding source live in `vendor/fastagent/docs/`, pinned from `fastagent-sh/fastagent`.
- Never edit `src/content/docs/docs/`, `src/generated/`, or `public/start.md`; `npm run sync:docs` regenerates them.
- `public/social-preview.png` is generated by `npm run og` from `scripts/render-og.mjs`, which holds the card as an SVG template. The card keeps its own colors — it is a poster seen alone in a feed, not a surface of the site — so it does not follow the palette. `public/favicon.png` has no source in the repo and bakes the page background into its tile, so a palette change means re-exporting it. The wordmarks (`logo*.png`) are transparent neutrals and follow no palette.
- The site palette lives in `src/theme.ts` (Catppuccin Mocha dark, Latte light). Two things stay outside it on purpose: third-party brand colors live with the ecosystem list in `src/pages/index.astro` (and their light-mode fixups in `site.css`), and the OG card keeps its own poster colors in `scripts/render-og.mjs`. `npm run tokens` generates `src/styles/tokens.css` from it — that file is generated, gitignored, and rebuilt before dev/check/build. The mode reaches the tokens as `color-scheme`, which `light-dark()` resolves, so there is one declaration per role and a subtree that must stay dark only sets `color-scheme: dark`. `npm run check` asserts the contrast floors, that every `--term-bg` pane pins that scheme, and that the committed rasters are current.
- Blog posts live in `src/content/blog/` (rendered by the custom blog pages, not Starlight).
- Keep the site static: Astro, Starlight, and vanilla CSS. Do not add a client framework, CMS, database, or SSR without a demonstrated need.
- Node 22.18 or newer: the build scripts import `src/theme.ts` directly, which needs the type stripping Node turns on by default from that version.
- Run `npm run check && npm run build` before opening a PR.
- Maintainer-authored PRs may self-merge after required checks; external-contributor PRs are reviewed and merged by a maintainer.
